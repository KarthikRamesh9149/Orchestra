# ADR-005: Shared workspaces without local identity or credential crossover

Status: accepted implementation direction under the authorized Step 6 plan; implementation and qualification incomplete.

Date: 2026-09-12. Decision owner: repository owner; implementation follows the approved eight-step contract.

## Context

Step 5 qualifies local Mac workspaces. Shared mode must use an authoritative operator-owned server, preserve existing DTOs and approval checks, and never upload local projects implicitly. Existing managed production is outside scope. Two separate computers are required for the final gate; the user confirmed only one Mac is currently available. This blocks that specific qualification, not implementation, and does not waive the gate.

## Decision

- A connection has a generated identity, explicit HTTPS origin and display name. Reject embedded credentials, URL paths/query/fragment, redirects and invalid TLS. No arbitrary renderer HTTP proxy.
- Before sending credentials, fetch and validate a bounded compatibility manifest from that exact origin. Reject unsupported protocol ranges and a changed persistent server ID. Server identity changes require explicit reconnection, not silently reusing a grant.
- Electron main owns per-connection encrypted credentials and refresh rotation. Never reuse installation-local actor tokens, provider grants or signing secrets for shared calls. Remote access is authenticated and authorized on every server mutation.
- Separate local and each remote connection's renderer session/cache namespace. Always show selected server/workspace. On logout/revocation, cancel in-flight work and clear associated cached state. Initial shared offline cache is disabled; optional administrator-enabled read-only caching remains a separately tested policy, never mutation replay.
- Serve packaged trusted UI, not remote HTML. Reuse DTOs through a reviewed remote method/path inventory. Shared mode does not gain generic filesystem, shell or network access.
- Self-host package keeps API/web, BullMQ worker, Redis, PostgreSQL/pgvector and private object storage. Operator supplies TLS, administrator bootstrap, provider/email configuration and backup targets. No staging flag or weakened managed-production validation.
- Export/import is an explicit authorized operation with hashes, provenance, accepted decisions and identity mapping. Credentials and unauthorized private chats are excluded; import cannot elevate unapproved evidence to truth.

## Alternatives and trade-offs

Loading arbitrary remote web content in Electron would reduce integration work but expand the renderer trust boundary. Sharing the local principal or browser token store is simpler but risks tenant crossover. Neither is accepted. Separate connection state and a narrow bridge cost more implementation but keep authority explicit and support reconnect/revocation testing.

A local two-profile test is useful for development but cannot substitute for the required two-computer qualification. No paid infrastructure or production deployment is needed for implementation.

## Completion checklist

- [ ] Versioned compatibility endpoint and exact-origin native transport.
- [ ] Protected remote sessions, refresh/revocation, role-aware workspace selection and isolated renderer state.
- [ ] Packaged shared UI journeys including streaming, uploads, approvals and private chats.
- [ ] Versioned self-host installation, TLS and owner bootstrap.
- [ ] Authorized transfer, identity mapping, backup/restore and populated upgrades.
- [ ] Failure/offline/compatibility/tenant tests.
- [ ] Two separate computers with different roles and authoritative shared evidence.

None of these rows is certified by Step 5's local checks.
