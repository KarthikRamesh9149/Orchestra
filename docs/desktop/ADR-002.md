# ADR-002: Portable local engine with transaction-fenced jobs

Date: 2026-09-10. Scope: Step 2, private Orchestra repository only.

## Context

The imported server uses inline/BullMQ jobs and optional Redis AI limits. Absent-key mock providers and fallback artifacts are unsuitable for an offline engine. Queue acknowledgement alone does not protect database effects after a crash.

## Decision

The local composition uses original services with PostgreSQL jobs/limits, private storage and unavailable AI providers. It inherits no process-environment credentials. Hosted signup is disabled. Installation authority is required in addition to normal actor/project authorization. Local identity onboarding remains Step 4.

Managed/self-hosted startup retains its worker. PostgreSQL queue selection without both injected dependencies fails closed. Local mode has explicit loopback, storage and distinct-secret validation, not a staging override.

Jobs use payload-bound idempotency, SKIP LOCKED claims, owner tokens, fences, expiry, bounded explicit retry and cancellation. The worker executes database effects and completion in one Serializable transaction; nested service transactions reuse it. A NO KEY UPDATE lock prevents reclaim but permits the cancellation-request foreign key. Cancellation is observed separately and rolls back pending effects. Healthy locked work is not stolen when its original lease timestamp expires. The dispatcher provides ownership-checked heartbeat for claims outside an active effect transaction.

Expired jobs become explicitly failed, not silently replayed. Reconciliation changes only unfinished matching document/research work, never accepted decisions or newer revisions. Explicit retry resets the matching failed domain transactionally. External effects are not described as exactly-once; provider qualification remains Step 5. Unconfigured generative jobs fail instead of publishing fallback artifacts.

The runtime role is neither owner nor superuser, has no BYPASSRLS, role/database creation, schema DDL or migration-history access. Explicit runtime RLS policies permit backend row access; services retain actor/tenant authorization. Migration administration is separate.

A dedicated one-connection advisory-lock session excludes another engine or backup on that database. Backup requires stopping the engine. AES-GCM/scrypt protects the database dump and files, excluding installation credentials. Restore requires an empty target and never overwrites a working installation. Privileged adapters are not renderer-provided commands. Supported backup bounds are 128 MiB of source data and 10,000 files; larger inputs fail explicitly.

## Alternatives and consequences

- Inline queue rejected: pending work would be lost.
- Acknowledgement-only fencing rejected: stale effects could still commit.
- Silent retry of arbitrary external operations rejected: recovery is explicit and bounded.
- Rewriting history rejected: 81 original migrations remain byte-preserved; two are additive.
- Transactions consume a connection and bound a handler to 120 seconds. This is a local correctness boundary, not a provider-latency claim.
- Bootstrap credential files are private, not an OS vault. Live files/database rely on OS disk encryption. Vault/native-runtime integration belongs to Step 3; Windows qualification to Steps 3/7.

## Verification and follow-up

STEP-2.md records reproducible checks. Tests cover actual process termination after a pending write, healthy-worker exclusion, retry, active cancellation, authenticated upload/download, offline citations, approval, restart and real database/file restore.

Packaged UI, real providers, shared teams, signing and publication remain separately owned by Steps 3–8. No production repository or deployment changes.
